# Helferlein: macOS upgrade and local data

The application ID (`com.invoiceapp.desktop`), product name (`Helferlein`), data key (`invoice-app:v1`), electron-store name (`invoice-app-data`) and existing encryption configuration are unchanged. The expected default macOS data location remains `~/Library/Application Support/Helferlein/invoice-app-data.json`; this path follows the unchanged Electron app identity and has not been certified on the user’s physical Mac. No login, network connection or external Node installation is required by the packaged runtime.

Before the first store initialization in a new app version, the existing encrypted file is copied unchanged to `invoice-app-data.before-<version>.json` in the same directory. A complete temporary copy is flushed and published exclusively; an existing version backup is never overwritten. A failure to create the first backup stops startup before defaults or migrations can write.

Any valid existing desktop snapshot is authoritative, including intentionally empty snapshots and settings-only data. An existing browser-local snapshot is retained unchanged. Only when the desktop data key is absent can the legacy browser snapshot be adopted. First adoption must durably preserve the source snapshot before writing the primary key. This does not merge conflicting records; preserve both snapshots and inspect/export them when reconciling an older browser-only installation. Random historical localhost origins cannot be enumerated through browser localStorage. If an old version used only browser storage at another port, export JSON from that version and import it through Backup.

Imports and explicit recovery save the previous raw snapshot before replacing it. Native recovery copies are separate immutable encrypted files, so historic copies do not need to be rewritten with every ordinary edit. Existing legacy recovery keys remain readable and may only leave the primary after their separate copies have been verified. The Backup page lists available native recovery points and offers JSON download before restoration. Update backups and user-created recovery archives are retained; automatic snapshots use a bounded seven-generation rotation in addition to a last-known-good copy.

Missing newly introduced collections are added in memory. Invalid existing collections, unknown schema versions and invalid JSON are rejected instead of becoming an empty account. Read failures must preserve the original file and report the error; recovery must never silently choose an older snapshot. If the whole encrypted store cannot be opened, startup stops and the original remains available for explicit recovery.

Desktop persistence is coordinated by one background storage actor. The renderer retains current edits while serialization, encryption and publication happen outside the UI process. “Saved locally” must refer to an acknowledged durable revision, not merely a queued edit. Normal close waits for the latest pending state; a failed flush keeps the app open and reports the failure. Force quit, process failure or power loss can lose changes that have not been confirmed. File and directory flushing improve durability where supported by the platform and filesystem, but are not a guarantee against every hardware failure.

Import success and automatic reload require successful persistence and flush. Before replacing existing data, the original-data backup must also have succeeded. If disk persistence fails, a manual JSON export can still rescue the current in-memory state; the page displays a warning instead of claiming that the app data was saved. Keep that downloaded file separately and keep the app open until the failure is resolved.

The checked-in synthetic fixture in `tests/runtime/fixtures/legacy-ae06259/` was generated using the historical `ae06259` initialization and actual electron-store 11.0.2 / Conf 15.0.2 encryption, with only the Electron OS environment stubbed. Its manifest records source, payload and ciphertext hashes. Integration tests decrypt that file, retain all seven collections, perform an unrelated settings edit, reopen and export, and confirm that the untouched last-good copy is still readable in the old format. Corrupt ciphertext, unsupported schema and invalid nested collections are tested without altering source bytes. A separate native Linux-Electron smoke (`node scripts/run-electron.mjs tests/native`) exercises the production preload, actual worker, immediate-close persistence, failed-close veto and retry. Neither proves the physical Mac upgrade. Measurements and failure guarantees are documented in [offline-performance.md](offline-performance.md).

## Release verification on real Macs

Before releasing an upgrade, test both Intel and Apple Silicon DMGs on supported macOS:

1. With the old app closed, copy the entire `~/Library/Application Support/Helferlein` folder to a safe location. Never test migration on the only copy of customer data.
2. Install the new app over the old one. Verify invoices, customers, products, attachments, logos, settings, recurring invoices, credits and templates against the old version.
3. Disable the network. Open, edit, export and import invoices, restart, and verify the last edit after closing immediately while typing.
4. Close the last window and reopen from the Dock; check standard macOS edit shortcuts and menus. A second launch should focus the existing instance.
5. Test disk-write failure on a disposable profile: error must be visible and normal close must preserve the pending snapshot. Test corrupt JSON/encrypted data and unsupported schema using copies only: startup must stop, without creating empty data over the original.
6. Verify JSON import creates a recovery copy, then test invalid JSON and malformed collections. Check that documents and settings are unchanged after a rejected import.
7. Confirm server binds only to 127.0.0.1, no remote requests are required, and startup succeeds with no system Node installation. Check packaging, macOS signing/notarization and Gatekeeper separately; CI building a DMG alone does not certify these.
